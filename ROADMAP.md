# Roadmap

The path from "works on my machine" to "the MiSTer community can
actually use this." Last updated 2026-05-28.

This roadmap describes both the **technical work** still to do and the
**distribution strategy** for getting vis_warp into people's hands.

---

## Current state (v3.1)

- ✅ RTL implemented, validated end-to-end on Template_MiSTer-VIS rig
- ✅ Bilinear interpolation in place for shipping-grade visuals
- ✅ Galaga consumer fork ready (build pending bilinear hardware validation)
- ❌ No Main_MiSTer userland (no OSD config, no preset INI)
- ❌ Not upstream
- ❌ No automated build pipeline
- ❌ Only one validated consumer core

This is enough to **demo**, not enough to **distribute broadly**.

## v3.4: Sync delay — proper implementation needed

**Status**: blocked. Two attempts (v3.3 counter FSM and v3.3b FIFO)
both failed empirically on hardware. See
[`POSTMORTEM-v3.3-sync-delay-2026-05-28.md`](./POSTMORTEM-v3.3-sync-delay-2026-05-28.md)
for the full debugging history.

**Why this matters**: without sync delay, the top ~20-30% of each frame
shows asymmetric/stale-buffer content. The bottom is clean. Affects
HUDs/score areas across most arcade cores. See
[`LIMITATIONS.md#0-top-of-frame-asymmetric-warp-v32-release`](./LIMITATIONS.md#0-top-of-frame-asymmetric-warp-v32-release).

**Why deferred**: agent-assisted implementations failed; this needs
careful design with simulation infrastructure and SignalTap probes
wired BEFORE writing RTL. The complexity is in:
- Multi-clock-domain ce_pix vs FIFO clk rate alignment
- ASCAL's input-lock behavior at startup (must see valid sync from t=0)
- Pipeline pixel-data vs sync-signal alignment through the warp stages

**Pre-requisites before retry**:
1. GHDL/Modelsim testbench that simulates vis_warp with synthetic
   timed input and verifies output sync edges
2. SignalTap probes on first hardware build (input sync, FIFO output,
   pipeline stages, ASCAL inputs)
3. Read POSTMORTEM thoroughly — specific guidance for the v3.4 retry
   in its "Pre-emptive guidance" section

**Estimated effort**: 2–3 days of dedicated work including sim setup,
not a "spend a few hours and see" task.

## v4: Main_MiSTer userland (highest priority after v3.4)

**Why first**: nothing else interesting happens until end users can
toggle vis_warp without recompiling. Hardcoded `reg_enable` and
`reg_curvature` values in `vis_warp.vhd` are the right dev-time
control but the wrong production user experience.

### Scope

**The RTL side is already register-ready.** vis_warp's `cmd 0x45` decoder
exposes three runtime registers — `reg_enable` (opcode 000), `reg_curvature`
(001), and **`reg_sharpness` (010, the sharp-bilinear K)** — each CDC-synced
and plumbed to the engine, defaulting to on / k=2 / K=2 until driven. v4 is
therefore *purely C-side*: translate OSD selections into `cmd 0x45` writes.

> **Why these are NOT per-core CONF_STR options:** vis_warp is a framework
> module in `sys_top.v`, which has no access to the emu's `status[]` bits
> (those live in `hps_io` inside the core). Framework video modules get
> their OSD config via the HPS command path — exactly how shadowmask works
> (`cmd 0x3E` + Main_MiSTer's global Video Processing menu). So warp
> enable/curvature/**sharpness** are global OSD items, available on every
> vis_warp-enabled core, not a per-core menu hack.

1. **`Main_MiSTer/user_io.h`**: add `UIO_SET_VISWARP = 0x45` constant.
2. **`Main_MiSTer/video.cpp`**:
   - `video_apply_viswarp_enable(uint8_t enable)`     → opcode 000
   - `video_apply_viswarp_curvature(uint8_t k)`       → opcode 001
   - `video_apply_viswarp_sharpness(uint8_t k)`       → opcode 010 (1=soft … 7=near-NN)
   - Preset INI keys: `warp=on/off`, `warp_curvature=0..7`, `warp_sharpness=1..7`
   - Per-core persistence: `<core>_viswarp.cfg`
3. **`Main_MiSTer/cfg.cpp` + `MiSTer.ini`**: `warp_default`,
   `warp_curvature_default`, `warp_sharpness_default` global defaults.
4. **OSD menu**: "Video Processing → Warp" submenu with **on/off**,
   **Curvature** (0–7), and **Sharpness** (Soft … Sharpest) sliders.
   (Auto-generated by Main_MiSTer's menu code; not in per-core `CONF_STR`.)

### Validation

- Build Main_MiSTer with the new handlers.
- Drop the binary on `/media/fat/MiSTer` (replacing the system binary —
  scary; back up first).
- Load Galaga-VIS, navigate OSD, toggle warp, change curvature.
- Confirm preset INIs work end-to-end.

### Upstream PR

Once v4 works, submit two coordinated PRs:

1. `MiSTer-devel/Template_MiSTer` — the RTL bits (sys/vis_warp.* + sys_top.v
   gates).
2. `MiSTer-devel/Main_MiSTer` — the userland bits.

PR body template (per the [framework reference](../memory/reference_mister_framework.md)):

> Adds vis_warp — a framework-level barrel-distortion video processor.
> Gated by `MISTER_WARP=1` macro so cores opt in. Tested with the
> Template demo rig + custom test patterns + Arcade-Galaga at k=0/k=2/
> k=7 on DE10-nano + DE10-nano-on-{1080p, 4K integer scale}.
>
> Screenshots: [link to release page].
>
> No regression in default behavior (macro unset = upstream-identical
> behavior, bit-exact).

Sole reviewer/merger: sorgelig. Acceptance not guaranteed; could be
rejected for scope/system-cost reasons (cf. PR #88 Sinden Border).

## Community distribution (parallel to v4)

Three escalating paths. They're complementary, not exclusive — you'd
typically progress through them in order.

### Path 1: This repo, local builds only

Where we are. End users would need:
- Quartus 17.0.2 Lite (16 GB install)
- This fork + a target core's fork
- 15–30 min compile per core
- Per-core SD card management

**Not a community story.** This is a "personal project / dev rig"
distribution. Useful only to people willing to do significant FPGA
toolchain setup.

### Path 2: Pre-compiled binaries on GitHub releases

We compile `.rbf`s for the cores we care about and post them as GitHub
release artifacts. End users:
- Download `.rbf` for the core they want
- Drop in `/media/fat/_Arcade/cores/`
- Use the existing MRA from their normal MiSTer setup
- ROMs come from their existing collection

This is what **most successful MiSTer enhancement forks do**. Cost:
- We compile every supported core for each release (manual or scripted)
- We host the binaries on GitHub releases
- We maintain compatibility as upstream evolves

**Target ship date**: as soon as bilinear validates on Galaga + at
least 2 other cores. Estimated 2 weeks of build work for ~10 cores.

### Path 3: GitHub Actions CI builds

Quartus 17.0.2 Lite installs cleanly in Linux containers. A GitHub
Action can:
- Clone each target core repo
- Apply our `sys/` patch + `.qsf` macro
- Run `quartus_sh` headless
- Upload `.rbf` artifacts to release pages
- Run on every push to main, every tag

Effort: ~1 week of CI engineering once Path 2 has proven the manual
build pipeline works.

Benefits:
- Fully automated releases
- New cores added in a matrix file
- Framework changes auto-rebuild all consumers
- Pull requests get build artifacts attached

Limits: GitHub free tier minutes for matrix builds (could move to
self-hosted runner if needed). Compile times are still 15-30 min per
core in CI, so a 10-core matrix = 2–5 hours wall clock per release.

### Path 4: Upstream merge to MiSTer-devel

The "permanent" path. Requires v4 first, then PR to sorgelig.

If accepted:
- Framework lands in upstream Template_MiSTer.
- Each arcade core's maintainer eventually syncs `sys/` and rebuilds
  (timeline: months — see Galaga's update history: 2021, 2023, 2024,
  2025-12).
- End users get vis_warp via the standard `update_all` script.
- Path 2/3 binaries become unnecessary for upstream-synced cores.

Risk: sorgelig may reject. Scope/system-cost rejections happen (PR #88
Sinden Border). Until upstream accepts, Paths 2/3 remain the
distribution mechanism.

## Framework version compatibility (the Galaga lesson)

When syncing this fork's `sys/` into a consumer core's tree, you need
to be aware of **how far behind upstream Template_MiSTer that core's
`sys/` is**. Older snapshots may have older `emu` port signatures
(narrower HPS_BUS, missing emu_ports.vh, different VGA_* layout).

Our experience syncing Galaga (snapshot circa 2024-05):
- Wholesale `sys/` replacement broke at the `emu` instantiation (49-bit
  HPS_BUS in Galaga vs 46-bit in current upstream).
- Solution: **surgical sync** — only the vis_warp files and the
  sys_top.v edits, keeping the rest of Galaga's `sys/` at its older
  snapshot to preserve the old emu API.

**Rule of thumb when adding a new consumer core**:

1. Compare the core's `sys/sys_top.v` `emu` instantiation against
   ours. If the HPS_BUS width and signal ordering match, full sync
   is fine.
2. If they differ, do a surgical sync (vis_warp files + carefully
   replayed sys_top.v edits + keep the rest of the core's `sys/`).
3. Always clear `db/` and `incremental_db/` before the first compile
   to avoid smart-recompile cache issues.

This is captured in detail in
[`HANDOFF-vis_warp-v3-kickoff-2026-05-28.md`](./HANDOFF-vis_warp-v3-kickoff-2026-05-28.md).

- MISTER_FB cores (Apple IIGS, etc.) — different rendering path, needs
  separate investigation
- Computer cores running ≥1024-wide modes (Amiga, ST) — bandwidth
  doesn't fit M9K, would need DDR3 path (explicitly rejected in design
  lock)

## What we are NOT planning

To set expectations:

- **No "warp shader" framework**. vis_warp is one specific effect
  (barrel distortion). A broader CRT-effects toolkit would be a much
  larger architectural undertaking.
- **No fork of every MiSTer core**. The community gets to choose which
  cores get the vis_warp treatment based on demand. Path 4 (upstream)
  is the path for "every core gets it."
- **No per-pixel-runtime configurability beyond on/off + curvature**.
  Anything more complex needs to live in a separate effects module.
- **No mobile-app / web-UI for the OSD**. MiSTer's existing on-device
  OSD is the user interface.
- **No commercial / paid version**. GPL v2+ all the way down.
